# F23 — A project's roadmap

## Problem it solves

A task list for several agents has two parts with opposite natures, and putting
them in the same place breaks one of the two.

A task's **definition** describes the code: it lives next to it, anyone who opens
the folder can read it, and its paths are relative to the repo's root. That
belongs to the project.

The **claim** — who is doing it right now — does not describe the code, it
describes this moment. And it has to be atomic: between one agent reading "free"
and writing "mine", another must not slip in. A file in git does not give that
guarantee: two agents read "free" at the same time and both believe they won.

The question that separates the two: **if I `git checkout` a branch from last
week, should this change?**

## What it is

A `TASKS/` folder in the project's repo, and three tools in the turn.

```
TASKS/
├── README.md                    the end goal + what is in each folder
├── 01-foundation/
│   ├── README.md                THIS group's goal
│   ├── 01-device-layer.md
│   └── 02-shell.md
└── _drafts/                     the raw output of some research,
    └── …                        unnumbered, waiting for the standardizer
```

### The folder is not committed

When Keel starts the session that defines the format, it adds `TASKS/` to the
project's `.gitignore` — with a comment explaining where the line came from — and
never touches it again. The roadmap is the working notebook of whoever is using
Keel, not a deliverable of the project: a file that moves every day dirties the
history and the PRs of the whole team to tell something only useful to whoever is
running it. The format prompt tells the agent this too, so it does not remove it
from the `.gitignore` on its own.

Two things the app deliberately does **not** do: it does not run `git rm --cached`,
so a `TASKS/` that was already committed stays that way until you remove it; and
it does not touch `.git/info/exclude`. If the project is not a git repo, it writes
nothing.

Expected side effect: when unifying a worktree, `TASKS/` appears in the "these
ignored files go with the folder" list. It is right that it appears — it is exactly
what git was not going to miss and you would.

**There is no `TOMADAS.md` or `SEGUIMIENTO.md`.** That is deliberate: a shared
state file is a conflict magnet, because every agent that finishes something writes
to the same destination. With the state inside each task, two agents finishing two
different tasks touch different files and never collide. Global tracking is
generated by reading the folder.

The `.md`'s format is deliberately minimal — a frontmatter of `key: value` pairs
and a `## Bloqueantes` section with checkboxes — so it can be written by hand,
reviewed by eye in a PR, and parsed without adding a YAML dependency. The template
is in `docs/templates/TASKS/`.

### Order and priority are not the same

The file's `NN-` says **in what order** to take things. `prioridad:` answers a
different question: **what happens if this does not get done**. A task can be third
in line and be the most urgent thing there is — because another project is stalled
waiting for it — and that cannot be read from its position.

Three values: `alta` (somebody is waiting), `media` (ordinary work), and `baja`
(it improves something that already works). If everything is `alta`, nothing is.

It is **optional**, and not out of timidity: the format check looks at nine things,
and making it mandatory would invalidate every folder that already exists in one
stroke. Undeclared it counts as `media` — and the reader distinguishes "media
because it says so" from "media because it said nothing", just as it already did
with `estado:`.

## Nobody can cross projects

Scope **is not an argument the model sends**: it comes from the URL the MCP server
was handed to that turn with (`/roadmap/<project>/<session>/<profile>`), just as
the plan's MCP already did. From the project comes its working directory, and that
directory is the project's identity.

The session is in the route for a concrete reason, and it is not symmetry: without
it the claim knows WHICH task and WITH WHICH agent, but not in which of the
project's open sessions. The project's status (F25) needs that third column, and a
claim that does not know where it lives forces guessing it.

A turn of project A cannot claim a task from project B even if it asks: it has no
way to name it. And the claim's key carries the project's path inside, so
`02-shell.md` in one repo and `02-shell.md` in another are different things.

## The claim is synchronous, and everything depends on that

`TaskClaimsViewModel.claimTask` is not `async`. Dart runs one isolate at a time, so
between the read and the write there is no `await` where another could slip in —
that, and nothing else, is what makes the operation atomic. LMDB persistence comes
afterward, unawaited: the decision was already taken in memory.

A claim **expires after 30 minutes**. It is not an extra: if an agent dies with the
task claimed, without expiry that task is stuck forever and nobody understands why.
Calling `claim_task` again on the same task renews it, so a long turn does not lose
it to the clock.

The claim stores the project, the task, the agent, and **the session**. What it does
not store — and used to — is the project's name twice over: when the station became
a project it became obvious that `stationName` and `projectName` wrote the same
value.

Claims are **not backed up** in the vault: restoring them on another machine would
revive locks on tasks nobody is doing.

## The tools

| Tool | What it does |
|---|---|
| `list_roadmap_tasks` | Reads the folder and returns tasks, state, blockers, and who has each one claimed |
| `claim_task` | Claims a task. Fails if somebody got there first, or if it has open blockers |
| `release_task` | Releases it. You can only release your own |

`list_roadmap_tasks` **does not cache**. An index stored in the database goes stale
on its own: a `git pull`, a branch switch, another agent adding tasks — and the
database shows the old snapshot. Walking the folder is cheap.

The server is only handed to a turn if the project **has** a `TASKS/` folder. A
project without a roadmap does not see three tools that do not apply.

## Renumbering without dragging the references

It is the most expensive failure mode: somebody renumbers a folder, does not update
the blockers that pointed there, and that task ends up stuck behind something
nobody can finish because it no longer exists. The symptom appears far from the
cause.

It could be asked in the prompt that whoever renumbers drags the references along,
but that **asks**; it does not guarantee. The reader detects it: after gathering
every task it makes a second pass and resolves each reference against the ones that
really exist.

- It accepts the full path (`01-foundation/02-shell.md`) and also the bare name
  (`02-shell.md`, or `02-shell`), because that is how anyone writes it.
- If it matches none → `missing`.
- If the bare name matches two tasks → `ambiguous`, instead of picking one.

A task with a broken reference **cannot be claimed**, and `claim_task` says exactly
which one is broken and what to do. It closes the door on purpose: there is no way
to know whether the dependency disappeared or merely changed name, and guessing in
either direction is wrong silently. What can be done is naming the problem.

## How it coexists with the session plan

It does not replace it: they are different granularities that compose.

| | Lasts | Lives in |
|---|---|---|
| Roadmap | Months | The repo |
| Claim | Minutes | LMDB |
| Session plan (F17) | An afternoon | The channel |

The cycle closes in the repo: the last thing the turn does is mark `estado: hecho`
in the `.md`, which is committed with the code that justifies it.

## Verification

1. A project with `TASKS/` and two tasks: `list_roadmap_tasks` returns them, with
   the README excluded and the blockers read.
2. A task with an open blocker is not claimable; marking it with `x` makes it so.
3. `claim_task` on an already-claimed one fails and names who has it.
4. Calling `claim_task` again on your own renews it, does not fail.
5. `release_task` on somebody else's is rejected.
6. Two projects with different working directories and a task of the same name:
   claiming one does not block the other.
7. A project without `TASKS/` does not receive the tools.
8. A blocker pointing at a nonexistent task marks the task as not claimable, and
   `claim_task` names the broken reference.
9. A blocker written with the bare name resolves on its own; if that name exists in
   two folders, it is left ambiguous instead of picking one.
