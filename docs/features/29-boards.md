# F29 — Boards: the UI an agent builds and you trigger

## Problem it solves

Testing your own app while writing it means typing the same `curl` by hand, with
the same expired token, for the twentieth time. And the things that are not a
`curl` — sending yourself an FCM notification to see what the phone does — are
worse still.

A **board** is a small screen for that: fields on top, buttons in the middle, the
response at the bottom.

## "GenUI" here is a pattern, not an SDK

No new dependency, no call to a service, no Gemini.

The interface is generated by **one of the agents you already registered** — the
project's member, in an ordinary session — reading your code or your OpenAPI and
writing a specification through a local MCP tool. The app renders it with real
Flutter widgets.

It is the same shape everything else here uses: the model describes, the app
executes. Which is why a board can be read, versioned, backed up, and fixed by
hand. It is not an opaque screen some service returned: it is data.

## What is inside it

```
Board
├── fields[]     what you fill in before firing
│                text | multiline | number | boolean | option | json | secret
└── actions[]    the buttons
    └── steps[]  what happens when you press
        ├── http     method, url, headers, body
        ├── command  command, args
        └── captures what gets stored for the next step
```

Templates are `{{key}}` and apply in the URL, the headers, the body, the command,
and each argument. What goes into the URL is encoded; what goes into the body or a
header is not — that is the difference between an `&` that separates parameters and
an `&` that is part of a name.

An argument is resolved **whole and separately**: a value with spaces is still one
argument, which is exactly what passing through a shell would break.

### Chained steps, and why they exist

The case that breaks the simple version is push. Sending an FCM notification
requires an access token that comes from a command and **expires in an hour**.
With a single HTTP request, the answer is pasting a new token every time.

```
1  command   gcloud auth print-access-token
             └─ stores the output in {{token}}
2  HTTP      POST .../messages:send
             Authorization: Bearer {{token}}
             └─ stores {{name}} from the response body
3  command   adb logcat -d -s FirebaseMessaging -t 20
```

A run **stops at the first step that fails**. Step 2 almost always uses what step
1 captured, so continuing would mean firing a request with an empty token against
your API: better a short error than a long consequence.

A capture that finds nothing, on the other hand, **does not fail the run**: the
next step will fail on the missing key, and that error says more.

## The agent builds; you fire

`lib/src/integrations/boards_mcp/` serves five tools, all of them for definition:
`list_boards`, `get_board`, `create_board`, `update_board`, `delete_board`. Scope
comes from the URL (`/boards/<project>/<session>/<profile>`), just like the plan,
the roadmap, and requirements: a turn cannot name a project that is not its own.

**There is no `run_board`, and it is not an oversight.** A board fires real
requests against your API and commands on your machine; that this comes from a
decision of yours, and not from a turn that got carried away at three in the
morning, is the only line that makes it usable.

Command steps are shown in full before running and are confirmed **the first time
per action**, not on every trigger: a dialog that always appears gets clicked
through unread.

A consultation turn does not receive these tools either: it comes to answer a
question and leaves, and letting it build a UI in somebody else's project is
exactly the kind of side effect a consultation should not have.

## The boundary

`parseBoardSpec` is the only path by which a board enters the system — from the
agent and from the form, which edits the same specification and receives the same
errors.

The validation that pays the most: **every `{{key}}` must be a field of the board
or something a PREVIOUS step captured**. Without that, the board saves tidily and
blows up only when you press it.

A key missing at run time is an error with its name inside, and it stops before
going out to the network. The alternative — sending a literal `{{field}}` —
arrives at your API as a strange request and has you looking on the wrong side for
half an hour.

## Where it lives

In the **sidebar, under its project**: its own section, sibling to Status and
Sessions. A board tests THAT repo's API, and moving it out of the project would be
asking you to remember which one it belongs to.

**Boards** is both a row and a screen. The row leads to the project's list in the
center area; the chevron on the left opens and closes the list in the menu. With
none, that screen is the one offering the two paths — asking Keel AI or creating
one by hand — which is where that explanation is useful: in the menu it was a
four-line note you could not press.

It is deleted from all three places: the × on its row, the card in the list, and
the bank. It used to be only in the bank, which is precisely the place you do not
go into when the spare one is right in front of you.

On the rail there is **Bank**, to see them all across projects and order them.

## What travels and what does not

| | Travels in the backup | Why |
|---|---|---|
| The board's definition | Yes | It is the same as a skill or a workflow |
| The last 20 runs | No | What your dev API answered is of no use to anybody |
| The secrets' values | No | They are referenced by name, as everywhere else |

A project that gets deleted **takes its boards with it**, unlike requirements:
without its working directory they test nothing, and leaving a button that fires
against something you no longer follow is worse than not having it.

## Verification

1. Ask a project agent for a board for an endpoint → it appears in the sidebar
   while the agent is still writing.
2. Run it → status, time, and formatted body.
3. A two-step board: `echo hello` captures `greeting`, step 2 sends it in the body
   → `hello` arrives.
4. A `{{field}}` that does not exist → the error names the key and does not go out
   to the network.
5. A 4xx stops it: the next step does not run.
6. An action with a command asks the first time and not the second.
7. Editing the specification by hand gives the same errors it would give the agent.
8. Export the backup → the board travels, its runs do not.
9. Delete the project → its boards go with it.
10. Delete the board you are looking at → the center area falls back to the list,
    not to a gap.
